## 1. Threat Model & CSRF Vectors

Cross-Site Request Forgery (CSRF) is an attack where a malicious web application causes a victim's web browser to perform an unwanted state-changing action on a trusted site where the user is currently authenticated.

In this platform, potential high-impact CSRF vectors identified and defended against include:

1. **Profile Manipulation:** Unsolicited alteration of candidate identity, job preferences, compensation requirements, or work authorization (`POST /profile`, `PATCH /api/profile`, `POST /profile/clear-preferences`).
2. **Resource Disconnection:** Forcing disconnection of verified GitHub installations or revoking access tokens (`POST /sources/disconnect`, `POST /connect/revoke-provider`, `POST /connect/tokens/:id/revoke`).
3. **Artifact Tampering & Deletion:** Unauthorized approval, promotional promotion, or deletion of candidate resume documents (`POST /resumes/:id/approve`, `POST /resumes/:id/delete`).
4. **Job & Application State Forgery:** Falsifying job application status or deleting tracking history (`POST /applications/:id/status`, `POST /applications/:id/delete`, `POST /jobs/save`, `POST /jobs/unsave`).
5. **Session Termination & Account Deletion:** Malicious logout or account erasure (`POST /auth/logout`, `DELETE /account`).

## 2. Multi-Layered Defense-in-Depth Architecture

The platform enforces a five-layer defense against CSRF:

```
[Incoming HTTP Mutation Request (POST, PUT, PATCH, DELETE)]
                            │
                            ▼
      [Layer 1: Safe Method Filter]
           - GET, HEAD, OPTIONS bypass CSRF immediately
           - Webhook HMAC signatures handled by specialized ingress
                            │
                            ▼
      [Layer 2: Sec-Fetch-Site Check]
           - sec-fetch-site === 'cross-site' => IMMEDIATELY BLOCKED (403)
                            │
                            ▼
      [Layer 3: Origin & Referer Host Whitelist]
           - Origin must match APP_URL, Host, or trusted loopback
           - "null" origin or malformed URLs => BLOCKED (403)
           - Untrusted Referer => BLOCKED (403)
           - Missing Origin in browser context (sec-fetch-mode) => BLOCKED (403)
                            │
                            ▼
      [Layer 4: SameSite Cookie Attributes]
           - Session cookie uses SameSite=Lax (or Strict), HttpOnly, Secure
                            │
                            ▼
      [Layer 5: Cryptographic Session-Bound Anti-CSRF Token]
           - Format: <256-bit Random Hex Nonce>.<HMAC-SHA256 Signature>
           - Bound strictly to active sessionId and server secret
           - Constant-time comparison (crypto.timingSafeEqual)
           - Cross-session reuse or forged signatures => BLOCKED (403)
                            │
                            ▼
            [Authorized Mutation Handler]
```

### Layer 1: Safe Method Filtering & Machine Protocol Exemption

- Safe idempotent HTTP methods (`GET`, `HEAD`, `OPTIONS`) never trigger CSRF validation, preserving universal browser page navigation.
- External webhook ingress (`/webhooks/*`) authenticates machine-to-machine requests using HMAC-SHA256 signatures over raw request payloads and is exempt from browser session CSRF checks.

### Layer 2: Fetch Metadata Request Headers (`Sec-Fetch-Site`)

- Browsers send `Sec-Fetch-Site` indicating the origin relationship (`same-origin`, `same-site`, `cross-site`, `none`).
- Any state-changing mutation with `Sec-Fetch-Site: cross-site` is immediately rejected with `403 Forbidden` (`CSRF_DETECTED`).

### Layer 3: Origin and Referer Strict Validation

- If the `Origin` header is present:
  - Must parse into a valid URL.
  - Its hostname must be contained in the trusted hostname set:
    - Hostname of configured `APP_URL`.
    - Hostname of the incoming `Host` header.
    - Standard development loopbacks (`localhost`, `127.0.0.1`, `[::1]`, `0.0.0.0`, `127.*`).
  - An `Origin` value of string `"null"` (e.g., generated by sandboxed iframes or cross-origin redirects) is explicitly blocked.
- If `Origin` is omitted but `Referer` is present, `Referer`'s hostname must match the trusted hostname set.
- If both `Origin` and `Referer` are missing during a browser session (detected via `sec-fetch-mode` or strict configuration), the mutation is rejected.

### Layer 4: Strict Session Cookie Flags

- Cookies are issued with:
  - `SameSite=Lax`
  - `HttpOnly=true` (inaccessible to client-side scripts)
  - `Secure=true` in production (`__Host-` cookie prefix enforced)
  - `Path=/`

### Layer 5: Cryptographic Session-Bound CSRF Tokens

- Implements the OWASP HMAC-Based Token Pattern:
  - A 32-byte (256-bit) cryptographically secure random nonce is generated via `crypto.randomBytes(32).toString('hex')`.
  - The nonce is signed using HMAC-SHA256 with the server's session secret and the specific authenticated `sessionId`:
    $$\text{signature} = \text{HMAC-SHA256}(\text{secret}, \text{sessionId} \mathbin{\Vert} \text{":"} \mathbin{\Vert} \text{nonce})$$
  - The resulting token format is `${nonce}.${signature}` (129 characters total).
- Token verification:
  - Validates token syntax (nonce length = 64 hex characters, signature length = 64 hex characters).
  - Recomputes expected signature using the active request's `sessionId`.
  - Compares signatures using constant-time comparison (`crypto.timingSafeEqual`), preventing side-channel timing attacks.
  - Cross-session reuse fails: a token generated for User A cannot be replayed in User B's session.
  - Tokens are embedded in HTML forms (`<input type="hidden" name="csrfToken">` and `<input type="hidden" name="_csrf">`) and passed in AJAX headers (`x-csrf-token`).
