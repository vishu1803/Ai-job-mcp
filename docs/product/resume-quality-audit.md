# Resume generation, structure and quality audit

Audit date: 2026-10-09. Scope: the checked-out implementation, controlled synthetic inputs and real local document compilation. This is an audit and repair plan, not a feature implementation or production acceptance. Existing authentication, evidence trust, immutable snapshots, signing and approval rules remain mandatory. Production remains **NO-GO** pending separate release gates.

## Assessment

Resume functionality is **PARTIALLY WORKING**. The application has a substantial structured, evidence-aware generation pipeline, encrypted source/version storage, PDF/TeX artifacts and review/download surfaces. It does not yet provide a complete resume-builder experience. Five template identifiers are metadata rather than five implemented layouts; DOCX export and a generated-resume editor are not implemented. Uploaded Word documents can lose structure before normalization. Important candidate data is dropped between the canonical snapshot and the renderer. Sparse profiles can produce a generic inferred summary that claims experience without source facts.

Real local Chrome fallback compilation succeeded for four synthetic snapshots; independently rendered pages show the actual output rather than only a source-string assertion. This is proof of that local renderer boundary, not authenticated end-to-end application preparation, live AI output, employer ATS compatibility or production readiness.

## Field and structure coverage

Identity and role fields have schema constraints; source experience/education/certification fields deliberately permit absent data. Date fields are plain strings rather than validated precision-aware dates. The root schema is strict; there is no arbitrary custom-section contract (`resume.schemas.js:673`).

## Writing quality

The implementation has evidence-aware fact inventories, claim planning, accomplishment composition, technology normalization, metric guards and a writing rubric. These are useful measurable building blocks. They do not establish excellent output across personas. Current fallback prose is generic, three sentences long regardless of available facts and contains unsupported experience phrasing for a fresh profile. A high rubric value must not compensate for unsupported biography or missing source data.

Production writing acceptance should be based on a retained benchmark of candidate-owned facts and expected omissions:

1. Every rendered achievement/technology/metric/role maps to an authorized source fact or explicitly labelled candidate claim; zero invented numerical outcomes.
2. No summary implies employment, experience, expertise or delivery history absent from source. Empty input must produce actionable input requirements.
3. Summary target: normally 35-65 words, adjusted to persona; no boilerplate inserted merely to meet length. No unsupported seniority.
4. Bullets: one readable accomplishment per item; normally 12-35 words; zero blank bullets; deterministic duplicate detection and no cross-project technology attribution.
5. Use consistent past/present tense for completed/current work. Grammar and tense require a human-rated reference set; regex heuristics alone are not a validated writing assessment.
6. Employer-specific titles and company claims must come from the target job or user facts, never inferred mission/funding/credentials.
7. Job keywords can only emphasize existing supported capability. Missing requirements must stay missing, with an explanation rather than keyword stuffing.

## ATS compatibility

The canonical design uses linear sections, selectable text, conventional bullets and authentic hyperlinks. Native TeX aims to embed Latin Modern and disable common ligatures. Chrome fallback instead uses system sans-serif fonts (`latex-compiler.service.js:604`), so native/fallback visual equivalence is not proved.

`resume-quality-assessment.service.js` correctly describes its deterministic metric as **our parser's parseability**, not an employer ATS score, and distinguishes job fit from evidence-backed coverage. This audit does not validate any universal ATS score. The separate review fallback RES-14 still contradicts that honest presentation.

Required ATS checks:

- Independently extract PDF text in page/reading order, compare canonical contact fields and all selected source content, and check fonts/unicode. Do not use only the same custom parser that produced the score.
- Preserve each selected employer/title/date, institution/degree, project and supported bullet; record intentional omissions as explicit decisions.
- Check no replacement glyphs, raw TeX, scrambled page chronology, invisible text or blank list items.
- Recognizable headings and dates; source-aware checks should not require work history for a student or phone/portfolio for every user.
- Publish only a versioned local parseability rubric and separately identified job matching/coverage calculation. Actual ATS vendor compatibility remains NOT VERIFIED until controlled vendor-specific tests exist.

## Measurable document acceptance targets

These are proposed product acceptance targets, not a vendor ATS scoring method or claims that current PDFs satisfy them:

- Body text at least 10pt; section headings distinguishable and consistent. Current observed 8.5pt text does not meet this proposed readability gate.
- Zero blank bullets, duplicated headings, unsupported numerical claims, missing selected source records, overlapping text rectangles or text outside usable page margins.
- Independent PDF extraction preserves 100% of required contact fields and selected employer/title/date/project/education text, with correct page order and no replacement glyphs. Report intentional source omissions explicitly.
- A one-page student fixture and a two-page experienced fixture must both pass actual raster/text inspection. Never achieve a page budget by silently dropping roles, facts or reducing type below the agreed minimum.
- Long titles, international names and long linked URLs must fit or wrap without changing link targets. The current evidence-blocked project fixtures do not prove this requirement.
- Dates use one validated precision-aware format; zero impossible months or reversed ranges. Current work/enrollment and past work remain accurately distinguished.
- Summary and bullet length targets are advisory; source integrity and grammar outrank a word-count target. Benchmark reporting separates factual correctness, writing quality, parseability, layout and job relevance.
